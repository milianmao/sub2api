# 账号存活检测弹窗设计

## 背景

账号管理页目前支持单账号连接测试，但缺少对当前账号集合的批量存活检测入口。管理员需要在一次操作中检测当前所有或当前筛选账号，检测完成后看到类似仪表盘的汇总数据，并让账号列表状态反映最新检测结果。

## 目标

- 在账号管理页提供“账号存活检测”入口，点击后打开弹窗。
- 弹窗内展示检测范围、检测进度、存活/异常数量、平均延迟、平台结果、失败原因和检测明细。
- 检测完成后回写账号状态，并刷新账号列表。
- 复用现有单账号测试能力，避免为每个平台重复实现探测逻辑。

## 非目标

- 不在账号管理页常驻新增顶部统计卡片。
- 不做后台定时自动检测。
- 不对所有数据库账号无条件自动探测；检测范围由当前筛选或选中账号决定。
- 不改变现有单账号测试弹窗的交互。

## 用户体验

### 入口

- 在账号管理页的工具操作区域新增“账号存活检测”。
- 若当前有选中账号，弹窗默认检测选中账号；否则默认检测当前筛选结果。
- 弹窗顶部明确展示检测范围，例如“选中 8 个账号”或“当前筛选 64 个账号”。

### 弹窗布局

弹窗采用仪表盘风格展示：

1. 检测控制区
   - 检测范围说明。
   - 并发、超时等执行提示。
   - “开始检测”按钮。
2. 指标卡片
   - 检测进度：已完成 / 总数。
   - 存活账号：成功数量和成功率。
   - 异常账号：失败数量。
   - 平均延迟：成功账号平均耗时。
3. 分布区
   - 按平台展示成功/失败数量。
   - 按失败原因展示错误分类，例如认证失败、额度/限流、超时、其他错误。
4. 明细表
   - 账号名称、平台/类型、检测结果、延迟、状态更新说明、错误信息。
5. 完成区
   - 检测完成后显示“完成并刷新”。
   - 可提供失败列表导出，作为低优先级增强，不阻塞首版。

## 检测语义

- 真实检测通过现有账号测试能力发起轻量请求。
- 批量检测由后端控制并发和超时，避免前端同时发起大量单账号请求。
- 检测结果分为：成功、失败、跳过。
- 跳过用于不支持检测、缺少可用测试模型或账号数据无效的情况。

## 状态回写规则

- 成功：将账号状态更新为 `active`，清空可恢复的错误信息，并尝试恢复可恢复的运行态限制。
- 失败：将账号状态更新为 `error`，写入检测错误摘要到错误信息。
- 跳过：不改变账号状态，在检测明细中说明原因。
- 已禁用或明确不可调度账号不自动改为 active，除非真实检测成功且该账号原本不是人为禁用状态。

## 后端设计

新增管理员批量检测接口：

- `POST /api/v1/admin/accounts/liveness-check`

请求体：

```json
{
  "account_ids": [1, 2, 3],
  "filters": {
    "platform": "",
    "type": "",
    "status": "",
    "group": "",
    "search": "",
    "privacy_mode": ""
  },
  "scope": "selected",
  "concurrency": 5
}
```

规则：

- `scope=selected` 时使用 `account_ids`。
- `scope=filtered` 时复用账号列表筛选条件解析账号集合。
- 后端对账号 ID 去重，并限制单次检测数量。
- 并发值使用服务端上限裁剪。

响应体：

```json
{
  "total": 64,
  "completed": 64,
  "success": 51,
  "failed": 9,
  "skipped": 4,
  "average_latency_ms": 842,
  "by_platform": {
    "anthropic": { "success": 22, "failed": 3, "skipped": 1 },
    "openai": { "success": 14, "failed": 4, "skipped": 0 }
  },
  "failure_reasons": {
    "auth": 4,
    "rate_limit": 3,
    "timeout": 2
  },
  "items": [
    {
      "account_id": 1,
      "account_name": "claude-pro-01",
      "platform": "anthropic",
      "type": "oauth",
      "result": "success",
      "latency_ms": 731,
      "status_before": "error",
      "status_after": "active",
      "message": "检测成功"
    }
  ]
}
```

实现约束：

- 复用 `AccountTestService` 的平台检测逻辑，提取一个非 SSE 的批量检测入口或复用现有 background 检测能力。
- 复用账号列表筛选/导出中已有的筛选解析逻辑，避免前后端筛选语义不一致。
- 检测过程中按账号隔离错误，单个账号失败不影响其他账号。
- 不返回敏感凭据或上游响应体原文。

## 前端设计

新增组件：

- `AccountLivenessCheckModal.vue`

集成点：

- `AccountsView.vue` 在更多工具或操作区新增“账号存活检测”入口。
- 弹窗接收当前选中账号 ID、当前筛选条件、当前列表账号数量等上下文。
- 前端 API 在 `frontend/src/api/admin/accounts.ts` 新增 `livenessCheck`。
- 类型定义放入 `frontend/src/types/index.ts` 或靠近账号 API 的类型位置，遵循现有项目习惯。
- 文案加入 `frontend/src/i18n/locales/zh.ts` 和 `en.ts`。

交互状态：

- 未开始：展示范围和开始按钮。
- 检测中：展示 loading 状态，禁用关闭以外的重复提交。
- 完成：展示仪表盘数据和明细，“完成并刷新”关闭弹窗并触发账号列表刷新。
- 失败：展示整体请求失败信息，但保留可重试入口。

## 测试方案

后端：

- 单元测试批量检测请求参数校验、账号 ID 去重、筛选范围解析、并发上限裁剪。
- 单元测试状态回写规则：成功、失败、跳过、人为禁用账号。
- 单元测试汇总数据：平台分布、失败原因、平均延迟。

前端：

- API 测试验证请求路径和请求体。
- 组件测试验证未开始、检测中、完成、失败状态渲染。
- `AccountsView` 测试验证入口打开弹窗、完成后触发列表刷新。

手工验证：

- 启动前后端开发环境。
- 在账号管理页打开“账号存活检测”。
- 分别验证选中账号和当前筛选两种范围。
- 执行检测后确认弹窗汇总数据、明细、账号状态刷新符合预期。
